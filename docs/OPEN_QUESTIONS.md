| D29 | Passwords are hashed with **scrypt** through the package's `PasswordHasher` (Node's `node:crypto`, OWASP parameters). The `AGENTS.md` rule "argon2 or bcrypt" was changed to match | Developer, 2026-11-22 |
| D30 | The portal and the API are planned to share one parent domain, so sign-in uses **HttpOnly session cookies**, not tokens kept in the browser. The real domain is not chosen yet (Q31) | Developer, 2026-11-22 |
| D31 | **The manager assigns the agent's counties when approving the registration** (at least one county). Counties can be changed later. Several agents may cover the same county. Which counties each agent really covers is still open (Q4); the manager enters them. Rejecting a registration disables the account (rows are never deleted) | Developer, 2026-11-22 |
| D32 | **Retry from UNRESPONSIVE:** the manager can move an unresponsive order back to `PLACED` or `CONFIRMED` to try again. The assistant's reading, to confirm: if the order had an agent, the agent is released so the order is confirmed and assigned afresh. The agent's own retry `UNRESPONSIVE → DISPATCHED` stays | Developer, 2026-11-23 |
| D33 | **Reassignment:** the manager can move an assigned order to another agent **before it is dispatched** (`ASSIGNED` or `RESCHEDULED`, never `DISPATCHED`), and not to the agent who already has it while it is still `ASSIGNED` (nothing would change). **From `RESCHEDULED` the manager may give it back to the same agent** who had it, because a failed first attempt may be the customer's fault, not the agent's (developer, 2026-11-23). After a D32 retry the previous agent can also be chosen again | Developer, 2026-11-23 |
| D34 | **Payment on delivery (replaces the "paybill" part of D5 for now):** the customer pays the **agent**, in **cash or M-Pesa to the agent's own account**. The agent later sends the money to the manager by paybill, M-Pesa or cash; that settlement step is not built (ROADMAP Phase 2). When marking Delivered the agent records the **method (CASH or MPESA) and the amount collected**. No M-Pesa transaction code is required for now. The amount may differ from the order total: it is accepted and **flagged to the manager**, not blocked (developer, 2026-11-23). Whether an agent may collect part now and the rest later is not covered and not built | Developer, 2026-11-23 |
| D35 | **Stock is per agent and centrally issued:** each agent carries their own stock, and the **manager sends it** to them (issues it) (developer, 2026-11-24). Stock is counted in units per agent and product in an append-only ledger. Delivery takes the ordered units out of the delivering agent's stock and is never blocked by missing stock (on-hand can go negative and is flagged). Assigning an order to an agent without enough available stock warns the manager, who can override. Returns to the company and count/damage adjustments follow the design in `DATA_MODEL.md`; how they happen in practice is still Q12 | Developer, 2026-11-24 |
| D36 | **Manager-created orders (US-11):** the manager can enter an order for a customer who reached him another way (phone, WhatsApp, in person): name, phone, county, location and bundle, plus an optional note. It is marked `MANAGER_CREATED` and **starts `CONFIRMED`**, because he has already spoken to the customer (the D21 phone-confirm step is done). Prices come from the bundles, but **the manager may set a different total**; a reason is then required and is kept in the order history, and the item lines keep the bundle price so the difference stays visible. Who may discount, and by how much, is not a client rule yet. There is no separate customer list (PR #13 proposal still open) (developer, 2026-11-25) | Developer, 2026-11-25 |
| D37 | **Re-enabling an agent:** the manager can restore a disabled agent (`POST /agents/:userId/enable`). They keep the counties they had and can sign in again; their sessions were ended when disabled, so they sign in fresh. A rejected registration (never approved, no agent profile) cannot be re-enabled; it would need a new registration. UNCONFIRMED with the client: whether a rejected person should be approvable later (developer, 2026-11-25) | Developer, 2026-11-25 |
| D38 | **Payments summary (manager report):** `GET /manager/payments/summary?from=&to=` totals what each agent has **recorded as collected**, split cash and M-Pesa, with a count. Dates are **Nairobi calendar days** (inclusive; Kenya has no daylight saving). It is a record of what agents said they collected, **not a balance owed**: handing money over to the manager (paybill, M-Pesa or cash) is not recorded yet (Phase 2 settlement). UNCONFIRMED with the client: whether the manager wants this per day, week or month (developer, 2026-11-26) | Developer, 2026-11-26 |
| D39 | **The storefront is English only for now** (answers Q23). Swahili can be added later as a second set of text, and would need wording the client approves (developer, 2026-11-26) | Developer, 2026-11-26 |
| D40 | **Storefront wording is neutral placeholder text until the client approves it (Q14).** The pages show the product name, bundle prices, a pay-on-delivery note and what happens next, with **no benefits and no health claims**. The product description and image slots stay empty until approved text arrives. All wording sits in one file, `apps/storefront/src/lib/copy.ts`. Struck-through "was" prices and "Save %" badges are not built (Q25 is unanswered) (developer, 2026-11-26) | Developer, 2026-11-26 |
